## Context

首頁與加入房間是兩個簡單頁面，但「加入」要改房間成員，和 room-lobby 共用 Room 資料。房間建立、房間大廳畫面由 room-lobby 負責；本規格只負責「把使用者加進房間並帶過去」。

## Goals / Non-Goals

**Goals:**

- 首頁兩個入口按鈕與近期開團列表。
- 房號、邀請連結兩種加入方式，四種拒絕情況各有提示。

**Non-Goals:**

- 完整的房間搜尋、篩選頁（分工表的「遊戲大廳（房間列表）」，不是 ⭐，另開規格書）。

## Decisions

### 搜尋團務先導向加入房間頁

設計稿沒有搜尋結果頁，第一階段「搜尋團務」直接開 TV-3 加入房間頁。完整搜尋頁做出來後再改導向。

### 加入在伺服器端檢查

滿員、已開始、已結束的判斷都在 `POST /api/rooms/join` 裡做，並在同一個資料庫交易內新增成員，避免兩人同時搶最後一個位子時超收。

### 近期開團只顯示公開房間

房間要有「公開」設定（room-lobby 的跑團設定）才出現在首頁，避免私人團被陌生人加入。

## Implementation Contract

- **行為**：首頁顯示主視覺、兩顆按鈕、近期開團卡片（不限張數、橫向捲動、可切換排序）；加入房間頁可用房號加入；`/join/<roomCode>` 可直接加入。
- **API**：`GET /api/rooms/recruiting?sort=scheduled|created` 回傳卡片所需欄位陣列（含 `createdAt`；`scheduled` 依開團時間由近到遠、`created` 依建立時間由新到舊；不限筆數）；`POST /api/rooms/join { roomCode }` 成功回 `{ roomId, destination: "lobby" | "game" }`，失敗回 404（找不到）或 409 加 `reason: "full" | "playing" | "ended"`。
- **失敗模式**：拒絕時頁面保留輸入的房號並顯示對應訊息。
- **驗收**：用 mock 資料走完 join-room 規格的拒絕原因表四列；兩個瀏覽器同時搶最後一席，只有一人成功。
- **範圍內**：首頁、加入房間頁、邀請連結路由、上述兩支 API。
- **範圍外**：建立房間流程、房間大廳畫面、完整房間搜尋頁。

## Risks / Trade-offs

- [room-lobby 還沒做好，加入後沒地方去] → 先導向一個顯示房號的暫時頁面，room-lobby 完成後換掉。
